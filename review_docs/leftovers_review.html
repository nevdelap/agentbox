Durable guardrails

Keep the product local: one host, one project/machine identity, the existing container and named-volume lifecycle, and the existing nested Docker runtime. Do not turn reports into a public compatibility protocol, or add distributed coordination, a workflow engine, a general process supervisor, an event store, or an unbounded history model.

Keep safety complexity that earns its place: fail-closed policy/mount snapshots, the existing per-project lock, atomic failure records, bounded best-effort update coordination, and the one-replacement nested-daemon readiness rule. The supported runtime matrix must stay finite and risk-based rather than Cartesian. Runtime cleanup must identify exact run-owned resources and refuse broad prefix/label deletion or uncertain ownership.

Keep boundary-distinct tests. Public command dispatch and pure projection/report tests are complementary, not duplicates. Likewise, outer-container recovery and inner-daemon-readiness runtime rows exercise different fault boundaries and should remain separate.
