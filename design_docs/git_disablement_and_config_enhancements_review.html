SPECIFICATION REVIEW

Agentbox Git Disablement

Final specification review of design_docs/git_disablement_and_config_enhancements.html. This report evaluates only what the proposed system must do, reject, preserve, or report; implementation work is out of scope.

Reviewed 2026-09-12 · Closing pass. No further findings are introduced by this document.

Final disposition: review closed.

The final recorded findings are S8–S16 below. They are preserved as specification follow-up for the design owners; this document does not open another review cycle or add further findings.

Current specification quality

Clear Core policy model

Precedence, field inheritance, command-specific persistence, canonical digests, legacy migration, and the ordinary-agent threat-model boundary are now coherent.

Clear Reconciliation safety

Running-container refusal, explicit apply, named-volume preservation, durable operation records, protected destinations, and one-way label migration are well specified.

Open Cross-state precedence

The command matrix, operation-record statuses, and nested-daemon readiness state machine are not yet combined into one authoritative decision order.

Open Host interface edges

Path canonicalization, source races, update throttling, retry identity, and stable command/report behavior still need explicit contracts.

Findings

IDSeveritySpecification gapRequired resolution
S8
Open		 High The authoritative matrix classifies only container presence, lifecycle, labels, and mounts. The apply contract separately says a non-complete operation record blocks ordinary execution, while the nested-Docker contract permits generic ab exec in some failed-readiness states. Consequently, “running valid, matching” can mean proceed or refuse depending on an unrepresented operation/readiness overlay. Define an ordered decision model that applies operation-record status and nested readiness after container/policy classification. Add matrix columns or an explicit overlay table for no record, active record, removal failure, absent-after-failure, network-degraded, readiness-failed, and each nested readiness state. State which commands are allowed, refused, or limited in every combination.
S9
Open		 High network-degraded is described as a recorded optional-network failure, but its lifecycle is undefined. It is not clear whether the replacement is considered complete, whether the record may be removed, whether ordinary start/exec may use the new container, or whether every later invocation retries the optional attachment. The rule that a failed record prevents ordinary execution could unintentionally block a usable container. Specify whether optional-network degradation is a warning on an otherwise usable completed container or a non-complete operation state. Define record retention/cleanup, command permissions, status and config output, retry timing, and whether the optional network is retried automatically, only by explicit apply, or never without a configuration change.
S10
Open		 High The canonical machine-name rule is internally contradictory: [A-Za-z0-9][A-Za-z0-9._-]{0,62}[A-Za-z0-9] requires at least two characters, while the following text says a one-character name is valid. This changes lookup paths and therefore policy selection. Replace the grammar with an exact rule that either explicitly permits one character or explicitly rejects it. State the maximum length, allowed first/last characters, treatment of a one-character name, and the exact diagnostic for an invalid value. Add examples at both length boundaries.
S11
Medium		 Medium The policy snapshot rechecks the files that were read, but it does not say whether the snapshot includes absent expected tier files. A previously absent file can appear between snapshot creation and mutation without being rechecked, changing the effective policy while the operation proceeds. The treatment of symlinked policy files or tier directories is also not stated, despite the “under the configuration tree” requirement. Include every expected tier path in the snapshot, including an explicit absent/type state, and recheck existence, type, and metadata before mutation. Define whether symlinks are rejected at every path component or resolved only when the resolved target remains inside the canonical configuration root. Report the source-change reason and retry behavior consistently.
S12
Medium		 Medium Credential sources are validated before mutation, but the snapshot/recheck contract covers policy files only. A grant directory or known_hosts can be replaced, retargeted through an entry inside the directory, or change type after validation and before Docker resolves the bind mount. The phrase “all-or-nothing” does not define the outcome of that race. Specify source identity and change handling for each grant: whether directory/file device and inode identities are captured, whether directory-entry symlinks are allowed, and whether a change causes a no-mutation retry/failure. Define whether the mount observes a point-in-time source or the live host path, and ensure the recorded grant is successful only under the stated guarantee.
S13
Medium		 Medium Protected-mount conflicts are defined by destination and obscuring parent, but path equivalence is not. Trailing slashes, ./.. components, repeated separators, case behavior, and Docker’s file-versus-directory target semantics could cause two syntactically different custom destinations to collide or evade the protected-path check. Define the canonical form used for every mount destination before conflict checking, including lexical normalization, path-component boundaries, case sensitivity, and rejection of relative destinations. State the result for a custom mount at each protected path, an exact parent, a child, and a merely similar name such as .ssh2; report the normalized path in diagnostics.
S14
Medium		 Medium The design requires stable diagnostics for policy and blocker errors and exact reports for deltas, but does not define the command protocol. Exit statuses, stdout versus stderr, whether ab config is human-only or machine-readable, and the behavior of status, logs, and config init are not consistently specified in the matrix. Define a small stable result contract for every policy-sensitive command: success/refusal/failure exit classes, diagnostic stream, required fields, redaction rules, and whether structured output is available. Add status, logs, and config init to the command-scope and lock/update/read-only rules, or explicitly mark them outside this feature.
S15
Medium		 Medium The update check is described as globally hourly-throttled, but only the per-project launcher lock is specified. Invocations for different projects or machines can race on the throttle state, and no location, atomic update rule, clock basis, failure handling, or behavior during an in-flight request is defined. Specify the host-wide throttle record and lock, its permissions and atomic update behavior, the time source and clock-rollback rule, and the result of concurrent or failed checks. Define whether a skipped/throttled check is reported and ensure the global update state cannot contain policy or credential data.
S16
Low		 Low Failure records store an image reference and retries may use ab start --apply or ab rebuild, but the specification does not say whether a retry must use the recorded image identity or may select a newer tag/build result. This matters after removal, when the old container is absent and the operation is no longer reversible. Define image identity for each command and failure phase: tag versus immutable digest, whether image selection is repeated, and which retry command is exact for each record status. State how a changed image is reported and whether a retry is allowed to alter image contents in addition to applying policy.

Resolved since the previous specification review

S1 · Edge-state matrix
Resolved Running legacy and stale/invalid rows are now separate, and rebuild reconciliation requires explicit Git policy input; --no-cache alone does not authorize ambiguous state.
S2 · Failure observability
Resolved Durable, privacy-preserving operation records now define phases, failure statuses, atomic updates, volume preservation, and explicit retry direction. Cross-state use of those statuses remains S8–S9.
S3 · Grant sources
Resolved Missing, unreadable, symlinked, empty, and unexpected GitHub/SSH/known-hosts sources now have explicit pre-mutation outcomes. Source races remain S12.
S4 · Policy TOCTOU
Resolved One immutable policy snapshot, source hashes, one retry, and a no-mutation repeated-change failure are now normative. Absent-file and symlink scope remains S11.
S5 · Nested readiness
Resolved The readiness state machine, 30-second bound, outer-container availability, one replacement attempt, and retry-cycle rule are specified. Its precedence relative to policy/operation states remains S8.
S6 · Locking
Resolved Identity, fallback paths, permissions, timeout, busy/failed diagnostics, covered operations, and non-recursive acquisition are now defined.
S7 · Document roles
Resolved Normative requirements, evidence, history, review disposition, and follow-up work are explicitly labeled and the normative contract takes precedence.

Final disposition

Review closed with S8–S16 recorded as the final specification follow-up list. The findings remain part of the review record and may be resolved by the design owners as part of the normal specification process; no additional review pass is implied.

The central product decision remains coherent: no-Git is an ordinary-agent workflow policy, not a hostile-user security boundary. This is the final review record for the current design.
