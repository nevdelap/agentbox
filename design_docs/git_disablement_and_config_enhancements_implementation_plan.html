Ordered implementation breakdown for the Git disablement and configuration enhancements.

Planning pass · Tasks 1–7 have executable specifications below; tasks 8–14 remain at breakdown level.

Planning boundary: The task table orders the work. Tasks 1–7 additionally define implementation scope, tests, and acceptance criteria for execution and review; tasks 8–14 remain a high-level breakdown and are not specified here yet. The full system design remains in the design document.

Focused verification begins with each task and is consolidated in task 12.

Executable specifications for tasks 1–7

Execution contract: Luna implements one task at a time in dependency order. Each task is complete only when its scope, tests, and acceptance criteria below are satisfied. A task must not silently expand into a later task; if implementation exposes a missing dependency or contradiction, stop at that boundary and report it for review. The mandatory baseline test command for every code task is bash tests/run.sh, plus bash -n bin/ab agentbox-entrypoint.sh tests/run.sh. Focused tests are added alongside the task that owns the behavior; task 12 later consolidates regression coverage.

Task 1 — Baseline and change inventory

Scope

  • Inspect bin/ab, agentbox-entrypoint.sh, tests/run.sh, tests/smoke.sh, runtime/git-disabled, README.md, and the design/review documents.
  • Record the existing command entry points: start, build, rebuild, claude, codex, bash, exec, config, and config initialization.
  • Map the existing policy, mount, label, container-inspection, and test seams that tasks 2–7 will use.
  • Do not change production behavior, interfaces, runtime assets, tests, README content, or design requirements in this task.

Deliverable

  • Produce the authoritative inventory artifact design_docs/git_disablement_and_config_enhancements_implementation_baseline.html, listing each inspected file, relevant function/section, current behavior, and planned task owner.
  • The artifact must contain exactly these sections: Repository files, Launcher entry points, Policy/mount/label seams, Test fixtures, Test seams, Baseline commands/results, Pre-existing changes, and Task ownership.
  • Test fixtures must name the four-tier policy tree, valid/invalid policy files, absent/stopped/running container inspections, legacy/valid/stale label sets, Git/GitHub/SSH source types, protected/custom mount targets, and Docker helper mocks used by tasks 2–7.
  • Test seams must name the pure functions, Docker/network helper boundaries, filesystem source checks, and entry-point dispatch seams each later task will exercise.
  • List pre-existing dirty changes separately; do not attribute them to Task 1.
  • Record the exact commands used for the baseline checks and their results.

Tests and acceptance

  • Run bash -n bin/ab agentbox-entrypoint.sh tests/run.sh and bash tests/run.sh without changing the result.
  • Acceptance requires the named baseline artifact to exist with all eight required sections, a complete file/entry-point/function inventory, separate pre-existing changes, recorded baseline commands/results, named fixture/test seams, and implementation ownership for tasks 2–7. Task 1 must not change feature behavior.

Task 2 — Git disablement and access policy

Normative references: Suggested precedence, Settings to make persistent, Command-specific grant semantics, and Policy-file contract.

Scope

  • Implement capture and validation of the policy control surfaces: --no-git, --grant-gh, --grant-all-of-dot-ssh, AGENTBOX_NO_GIT, AGENTBOX_GRANT_GH, and AGENTBOX_GRANT_ALL_OF_DOT_SSH. Capture them consistently for start, build, rebuild, claude, codex, bash, and exec.
  • Represent each input as unset, true, or false where the control supports false; preserve the distinction between unset and explicit false.
  • Accept host boolean spellings 1, true, yes, on, 0, false, no, and off, case-insensitively. Reject every other non-empty value.
  • Keep update-check controls out of this task; they are owned by Task 10.

Boundary

  • This task owns the named CLI/environment/config control-surface interface and raw CLI/environment capture only; it does not parse or merge persistent files.
  • Its output is a raw policy-input record with exactly these fields: cli_git_enabled, cli_grant_gh, cli_grant_ssh, env_git_enabled, env_grant_gh, and env_grant_ssh. Each field is unset, true, or false.
  • Task 5 owns merged persistent resolution, defaults, labels, digest, and migration.
  • Task 6 owns command-specific state decisions; Task 7 owns mounts and lifecycle mutation.
  • Invalid input must be reported before any Docker, network, update-check, build, or container mutation.

Tests

  • Add shell-unit cases to tests/run.sh for every accepted boolean spelling, unset values, explicit false values, repeated flags, each supported command form, and invalid values.
  • Test that policy values are read from the host launcher environment and are not taken from container env files.
  • Test that invalid policy input exits non-zero and invokes no Docker or network helper, using mocked helpers/counters.

Acceptance criteria

  • All six named controls are captured consistently across supported entry points.
  • Unset, false, and true remain distinguishable until the resolver consumes them.
  • Invalid values have deterministic non-zero failure and no side effect.
  • The raw policy-input record has the six named fields and is consumable by Task 5 without reparsing CLI arguments or environment variables.
  • No persistent merge, mount, label, or container-state behavior is implemented under this task.

Task 3 — Identity, mount safety, and source consistency

Normative references: Canonical configuration lookup, Protected mount destinations and conflicts, Policy snapshot and source-change consistency, and Update-check scope and concurrency.

Scope

  • Canonicalize the machine name with ^[A-Za-z0-9](?:[A-Za-z0-9._-]{0,62}[A-Za-z0-9])?$; permit one-character names, permit at most 64 characters, and reject separators, whitespace, and all other characters.
  • Resolve AGENTBOX_DIR to an existing physical absolute path before project-tier lookup. Remove dot components and resolve symlinks; failure to resolve the project directory is fatal.
  • Use the physical project path plus machine name as identity. Preserve UTF-8 path components literally under projects/; do not case-fold or Unicode-normalize.
  • Canonicalize every custom mount destination as an absolute lexical path: collapse repeated separators and ./.., reject relative paths and paths escaping the container root, and compare path components without prefix-string matching.
  • Snapshot all four expected policy-file paths, including absent files. Existing policy files must be regular, readable, non-world-writable, non-symlink files; symlinked tier directories or policy files are rejected rather than followed.
  • For requested grant sources, capture the source type and identity before Docker work and recheck it immediately before mutation. Top-level ~/.config/gh, ~/.ssh, and known_hosts symlinks are rejected. Symlinks inside an accepted grant directory are not recursively validated by this task.
  • Implement the per-project advisory lock required before snapshotting: identity is SHA-256 of physical project path, NUL, and machine name; use $XDG_RUNTIME_DIR/agentbox/locks/<hash>.lock, then $XDG_CACHE_HOME/agentbox/locks/<hash>.lock, then ~/.cache/agentbox/locks/<hash>.lock; use directory mode 0700, file mode 0600, a 30-second bounded wait, and distinct busy/lock-failed outcomes.

Boundary

  • This task owns identity, canonical path comparison, source snapshot/recheck, and preflight rejection.
  • Its output is a locked canonical-context record containing the physical project path, machine name, four policy-source states, grant-source identities, and normalized mount destinations. Tasks 4–7 consume this record and must not recompute identity independently.
  • The lock handoff has exactly these logical fields: lock_path, lock_identity, lock_result (acquired, busy, or failed), lock_timeout_seconds=30, and a held lock handle for the operation lifetime. Task 10 reuses this handle and adds host-wide update coordination; it must not implement a second per-project lock.
  • Task 4 owns creation of policy mounts after these checks pass.
  • Task 5 consumes canonical identities for persistent policy lookup and metadata.
  • A source identity/type change causes one complete resnapshot/recheck; a second change fails with no Docker mutation.

Tests

  • Test one-character, 64-character, 65-character, invalid-character, and path-containing machine names.
  • Test physical-path resolution for symlinks, spaces, Unicode, nested paths, same basenames, dot components, and case-sensitive distinctions.
  • Test mount-target normalization for exact protected paths, parents, children, repeated separators, dot components, relative paths, and similar names such as .ssh2.
  • Test absent, regular, symlinked, directory, unreadable, and world-writable policy sources, plus source replacement between snapshot and mutation.
  • Test lock identity/path selection, directory/file permissions, acquisition, reentrant use by child operations, 30-second timeout, busy outcome, and lock-failed outcome.

Acceptance criteria

  • Every lookup and protected-mount comparison uses one canonical identity/path function.
  • No invalid machine, project, policy-source, or mount-target input reaches Docker or the network.
  • A source change is retried once from a complete new snapshot; a repeated change fails without mutation and identifies the changed source.
  • Every Task 2–7 policy-sensitive operation acquires the same per-project lock before reading the snapshot; no operation proceeds unlocked.
  • All listed path and source-type tests pass under bash tests/run.sh.

Task 4 — No-Git blocker and credential mounts

Normative references: What “disable Git” might mean, Leading implementation candidate: mount-based Git blocker, Credential-grant source validation, and Protected mount destinations and conflicts.

Scope

  • Validate the tracked runtime/git-disabled asset as a regular, non-symlink, readable, executable, non-world-writable file with mode 0755, resolved relative to the launcher root.
  • When Git is disabled, mount that asset read-only over /usr/bin/git. When Git is enabled, do not add the blocker mount.
  • When Git is disabled, omit both ~/.gitconfig and ~/.config/git/config mounts.
  • When GitHub access is granted, mount the validated ~/.config/gh source. When full SSH access is granted, mount ~/.ssh read-only and known_hosts read-write only when the validated host file exists and is writable.
  • Reject custom mounts that target or obscure protected policy destinations.

Boundary

  • This task owns mount construction, blocker asset integration, and mount-invariant validation after Task 3 preflight. Its output is a deterministic container-mount specification with exactly these entries: git_blocker, git_config, github_config, ssh_dir, known_hosts, and custom_conflicts; each entry records source, destination, and absent/ro/rw state.
  • It does not own container recreation or persistence of project/jj/Docker state; those are Task 7 lifecycle acceptance invariants.
  • It does not claim to block alternate Git binaries or hostile-user bypasses outside the protected destinations.

Tests

  • Mock mount construction for Git enabled/disabled, GitHub grant enabled/disabled, SSH grant enabled/disabled, and all combinations.
  • Test blocker missing, unreadable, non-executable, symlinked, world-writable, and wrong-mode failures.
  • Test exact protected-mount conflicts and verify no custom mount can shadow a policy destination.
  • Do not run container-runtime or end-to-end checks in this task. Those checks are owned by Task 13; Task 4 covers their corresponding mount-specification cases through mocks and inspection of generated mount arguments.

Acceptance criteria

  • When git_enabled=false, the generated mount specification contains one read-only git_blocker entry with source runtime/git-disabled and destination /usr/bin/git; when git_enabled=true, that entry is absent. The blocker’s exact output and non-zero runtime exit are accepted by Task 13.
  • When git_enabled=false, the generated mount specification omits both protected Git-config destinations; when git_enabled=true, it preserves the existing Git-config entries. It contains no entry that targets or obscures the workspace, collocated .git, jj configuration, or jj state destinations.
  • Credential mounts are present only when explicitly granted and only after source validation.
  • The mount specification leaves the workspace, collocated .git, jj configuration, and jj state destinations unmasked; lifecycle persistence across recreation is accepted by Task 7 and runtime-verified by Task 13.

Task 5 — Policy persistence and container metadata

Normative references: Proposed persistent policy config, Policy-file contract, Canonical digest and legacy-label migration, and Policy-label versioning and migration.

Scope

  • Read the four exact policy paths: global ~/.config/agentbox/agentbox.toml, machine, project, and machine/project tiers.
  • Parse only the four supported fields: git.enabled, github.grant, ssh.grant_all, and updates.check. Accept blank/comment-only files, LF/CRLF, exact table headers, boolean values, and trailing assignment comments; reject unknown/duplicate/unsupported syntax.
  • Merge fields from global to machine to project to machine/project, with later defined fields overriding earlier fields. Apply CLI over host environment over merged files. Use Git enabled, grants disabled, and update checks enabled as new-container defaults.
  • Compute the exact canonical policy digest over schema version, Git enabled, GitHub grant, and SSH grant; exclude update checks and source formatting.
  • Produce the values for exactly these version-1 policy labels: org.agentbox.policy.version=1, org.agentbox.policy.git_enabled, org.agentbox.policy.github_grant, org.agentbox.policy.ssh_grant_all, and org.agentbox.policy.digest. Parse and classify recorded labels, but leave label emission and mount-consistency verification to Task 7. Migrate valid old grant labels only when no new labels exist; classify malformed, partial, unsupported, contradictory, or digest-mismatched state as stale/invalid.

Boundary

  • This task owns merged policy values, source reporting, labels, digest, and legacy migration.
  • Its output is one resolved-policy record with exactly these top-level fields: effective values git_enabled, github_grant, ssh_grant_all, updates_check, and digest; four source-tier/value entries named global, machine, project, and machine_project; label_values containing exactly org.agentbox.policy.version, org.agentbox.policy.git_enabled, org.agentbox.policy.github_grant, org.agentbox.policy.ssh_grant_all, and org.agentbox.policy.digest; and recorded_state.
  • recorded_state contains exactly classification (absent, legacy, valid, stale, invalid, or unsupported-version), lifecycle_state (absent, stopped, or running), and mount_consistency (unknown, matching, or contradictory). Task 5 never emits a command decision or performs lifecycle mutation.
  • Task 2 supplies raw control values; Task 3 supplies canonical paths and source checks; Task 6 consumes the resolved policy for command decisions.
  • Do not stop, remove, recreate, or mount containers in this task.

Tests

  • Test all four tiers, field-level inheritance, explicit false overrides, CLI/environment precedence, unset values, new-container defaults, and command-family omissions.
  • Test every accepted and rejected grammar form, exact error location/reason, CRLF input, duplicate assignment, unknown table/key, and invalid host boolean.
  • Test canonical digest bytes and expected hash, equivalent-policy equality, and every container-affecting value change producing a different digest.
  • Test legacy labels, valid complete labels, missing/partial/malformed/higher-version labels, supplied mount-consistency classifications, and digest mismatch classification.

Acceptance criteria

  • The same effective input always produces the same merged values and digest regardless of file formatting or source tier.
  • Every invalid policy or label state is reported before mutation and is never silently guessed.
  • The resolved-policy record contains the contributing files, source tiers, effective values, digest, label values, and recorded-state data required by Task 6 and the Task 9 ab config presentation.
  • Task 6 can consume the named resolved-policy fields and recorded-state classification without parsing policy files or Docker labels itself; Task 7 is responsible for emitting labels only after the Task 4 mount specification is applied and verified.

Task 6 — Git policy state and command decisions

Normative references: Launcher entry-point policy scope, Authoritative state and command matrix, Apply atomicity and failure recovery, and Policy-label versioning and migration.

Scope

  • Implement one shared read-only classification before Docker/network/update work for start, start --apply, build, rebuild, exec and convenience commands, and config.
  • Classify containers as absent, stopped/running legacy, stopped/running valid matching, stopped valid different, or stopped/running stale/invalid.
  • Implement the exact command outcomes in the design matrix: ordinary running mismatch refuses; explicit apply reconciles; stale/invalid stopped state requires explicit apply or explicit Git reconciliation input for rebuild; config never mutates.
  • Preserve ordinary policy-free start state for existing containers. For rebuild, omitted grants resolve false; Git state is preserved unless an explicit Git policy input is supplied. --no-cache alone is never reconciliation intent for ambiguous Git state.

Boundary

  • This task owns the decision table and pre-mutation refusal/proceed/apply choice.
  • Its input record is the Task 2 raw policy input, Task 3 locked canonical context, Task 5 resolved policy, recorded-state classification, read-only container inspection, and any pre-existing Task 7 operation overlay. The overlay is explicit: operation_status is one of none, in-progress, removal-failed, absent-after-failure, network-degraded, readiness-failed, or complete; readiness_result is not-applicable, ready, failed-but-running, or failed-and-exited. Missing operation records are represented as none/not-applicable, not guessed from container state.
  • Its output is exactly one decision kind: create, start-in-place, reconcile-stopped, reconcile-running, build-recreate, refuse, or report-only, plus reason_code, mutation_allowed, execution_allowed, explicit_exec_mode (allowed, diagnostic-only, or blocked), update_allowed, and explicit_apply_required.
  • The mapping is fixed: absent lifecycle maps to create; stopped matching maps to start-in-place; stopped different maps to reconcile-stopped; running matching maps to start-in-place; running legacy maps to start-in-place only when inferred mounts match, otherwise refuse; explicit apply on a mismatch maps to reconcile-stopped or reconcile-running; build/rebuild maps to build-recreate; config maps to report-only; and stale/invalid state without the required explicit input maps to refuse.
  • After the base state matrix is evaluated, the operation/readiness overlay below is applied before execution_allowed can be true. A non-complete Task 7 operation or failed readiness result therefore cannot be bypassed by a matching policy/container row. This is a decision gate only; Task 7 owns lifecycle recovery and terminal record updates.
  • Task 7 performs the allowed Docker lifecycle operation and owns the minimum durable operation record/readiness interfaces; Task 8 later adds cross-command reporting/recovery integration; Task 9 later presents command-facing results.
  • Every decision must consume one immutable resolved policy snapshot and one read-only container inspection.

  • Each supported command/state combination has exactly one deterministic outcome.

Task 7 — Policy application and recreation

Normative references: Authoritative state and command matrix, Apply atomicity and failure recovery, Protected mount destinations and conflicts, and Nested-Docker restart recovery contract.

Scope

  • Apply the resolved policy to absent and stopped containers, and implement explicit stop/remove/recreate for running containers.
  • Use the existing image for policy-only recreation; do not rebuild the image solely because Git or a credential mount changed.
  • Preserve the project bind mount, named inner-Docker volume, and jj volume across policy recreation. Do not promise preservation of container-local filesystem changes.
  • Consume the Task 3 canonical context, Task 4 mount specification, Task 5 resolved policy/labels, and Task 6 decision. Construct the complete container arguments from those records; do not recompute policy or mount destinations.
  • Preserve the existing network selection and attachment semantics: the default/required network failure is fatal, while explicitly optional extra-network failure is returned as a degraded result for Task 8; do not redesign networking in this task.
  • Perform preflight, blocker/source validation, and read-only inspection before the first Docker mutation. Create the durable operation record before any create or before removing an existing container, then update it before and after each lifecycle phase.
  • Use the exact operation-record location and permissions from the design: $XDG_STATE_HOME/agentbox/operations/<sha256(physical-project-path + NUL + machine)>.toml, defaulting to ~/.local/state, directory mode 0700, record mode 0600, temporary-file-plus-atomic-rename writes, and no credential/policy-file contents.
  • The operation record fields are operation_id, started_at, optional completed_at, phase, status, container_name, optional old/new container ids, policy_digest, image_reference, named-volume names, network outcomes, and diagnostic. Phases are preflight, removal, creation, required-network, nested-readiness, and completion; statuses are in-progress, removal-failed, absent-after-failure, network-degraded, readiness-failed, and complete.
  • Expose a readiness adapter with exactly the outcomes ready, failed-but-running, and failed-and-exited. The adapter must verify the outer container and invoke the current nested-Docker readiness hook; Task 11 later supplies the expanded nested-daemon state machine behind this same interface.
  • Task 7 is complete only after the operation record exists before mutation, all required Docker phases have been attempted, the new container’s mounts and labels match the Task 4/5 outputs, and the readiness adapter returns ready. Task 7 failure leaves the terminal record in place; Task 8 may present or clean it only under the record status rules.
  • Its handoff is an operation_result containing the record path, terminal status, task_status (pass, fail, or degraded-fail), agent_execution (allowed or blocked), explicit_exec (allowed, diagnostic-only, or blocked), retry command, record_cleanup (permitted or forbidden), container name/id when known, failed phase when applicable, readiness result, network outcomes, image reference, and preserved volume names.

Boundary

  • This task owns Docker stop/remove/create/start/reconcile mechanics, the minimum durable operation-record lifecycle required before mutation, and the readiness-adapter seam for Git-policy changes.
  • Task 6 decides whether this task may run. Task 8 adds cross-command reporting/recovery integration to the record this task creates; it does not make the record optional.
  • Task 11 replaces the readiness adapter’s nested-runtime implementation with the detailed recovery state machine; it does not remove Task 7’s readiness requirement.

Acceptance criteria

  • A policy change produces the same logical container name and preserves the project, jj, and inner-Docker named volumes.
  • Policy-only apply does not invoke image build or destroy named volumes.
  • Every created container has mounts and labels matching the resolved policy snapshot.
  • Every policy-application operation creates and updates its durable operation record before its first Docker mutation; a successful record is cleaned up only after mount/label inspection and readiness succeed.
  • Failures stop before unauthorized later phases and expose phase/container/volume information through the Task 7 record for Tasks 8 and 9.
  • Each terminal outcome has exactly one operation result and permission set from the handoff table; no later task needs to infer whether the container may be used or the record may be removed.
