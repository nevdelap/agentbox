Goal

Allow users to control Git availability and GitHub credential access inside Agentbox either for one invocation/container or as persistent defaults. The primary use case is a jj-first workflow: when Codex or Claude cannot find the git command, they should naturally use jj instead of silently falling back to Git.

Possible control surfaces

Per-agentbox CLI option

ab start --no-git
ab rebuild --no-git

Best for an explicit, one-off choice. The option should be accepted anywhere the container is created or recreated.

Persistent config

git.enabled = false

Could live in the existing global/per-machine/per-project configuration hierarchy, allowing defaults and scoped overrides.

Environment variable

AGENTBOX_NO_GIT=1
AGENTBOX_GRANT_GH=1

Useful for automation, shell profiles, and environments where the behavior should be inherited automatically. These should correspond to the existing CLI controls.

Suggested precedence

  1. Explicit CLI value for the current command.
  2. Host launcher environment variable (not a container env file entry).
  3. Field-level merged agentbox.toml value, from global to most-specific tier.
  4. Default: Git integration enabled.

The controls are intentionally asymmetric. Git is available by default and only needs an opt-out: --no-git / AGENTBOX_NO_GIT=1. Grant settings are opt-in only: GitHub and full-SSH access default to off, and a positive CLI/env/config setting enables them. No positive --git flag is needed by design. If a broader policy disables Git, a more-specific TOML value of git.enabled = true or AGENTBOX_NO_GIT=0 re-enables it for that invocation; this is an environment/config override, not a new CLI opt-in.

“Unset” is distinct from false. For a new container, Git defaults to enabled, grant settings default to disabled, and update checks default to enabled. For an existing container, an omitted git.enabled or grant policy preserves the corresponding state recorded on that container when using ordinary ab start, so a policy rollout cannot silently change security mounts. An explicit false from a more-specific TOML file or host environment revokes an inherited or persisted grant; AGENTBOX_NO_GIT=0 or git.enabled = true explicitly re-enables Git. The positive grant flags remain opt-in and have no negative CLI counterpart.

Command-specific grant semantics

The compatibility rule is intentionally command-specific. Ordinary ab start, including the start path used by ab claude, ab codex, ab bash, and ab exec, treats an omitted Git or grant policy as “preserve the persisted state if one exists.” In contrast, ab build/ab rebuild retain the existing documented behavior: when no grant flag, host grant variable, or TOML grant value is supplied, the rebuild resolves both grants to false and recreates without them. For Git, a policy-free rebuild preserves the recorded state unless the rebuild explicitly receives --no-git, AGENTBOX_NO_GIT, or git.enabled; this avoids making a routine rebuild unexpectedly enable Git in a no-Git agentbox. An explicit positive grant flag or policy value enables the grant, and an explicit false revokes it in either command family. This preserves the established explicit-rebuild grant-revoke workflow without making an omitted ab start unexpectedly change security mounts.

Threat model: no-Git mode targets ordinary agent command discovery and normal tool behavior, not a hostile user trying to bypass the policy. The primary git command is masked; Git helper executables, alternate Git binaries, and user-supplied mounts are outside this first version’s guarantee and must not be described as comprehensively blocked.

Relationship between gh and no-Git mode

gh does not require the git executable for all operations. API-oriented commands such as authentication, API queries, issue/project/release operations, and remote repository administration can remain useful. However, commands that manipulate a local checkout invoke Git or depend on local Git repository context. On a jj-first repository, those local Git operations should not happen: no-Git mode intentionally makes them fail instead of allowing gh to operate on the collocated .git metadata behind jj’s back.

gh has its own configuration under ~/.config/gh; it does not generally use ~/.gitconfig as its configuration store. Git-dependent gh commands do invoke the separate git process, however, and that process would normally read ~/.gitconfig. Omitting the Git config mount in no-Git mode is therefore consistent: preserve gh configuration and credentials, but do not provide Git configuration for a Git process that should not exist.

gh operationNo-Git impact
gh repo cloneUnavailable; it runs Git clone locally. Use jj-native repository setup instead.
gh pr checkoutUnavailable; it checks out a pull request using Git. Use jj commands/workflows for local changes.
gh repo fork --cloneUnavailable or partially unavailable because the local clone step needs Git.
gh repo create --source / --pushUnavailable or limited when the operation needs a local Git repository or Git push; use jj and an explicit remote/API workflow instead.
API and remote-only commandsGenerally remain available, especially when the repository is supplied explicitly with -R OWNER/REPO rather than inferred from local Git state.

Therefore --grant-gh should remain independently controllable and should not be rejected by --no-git. The design should describe no-Git mode as “Git unavailable; GitHub CLI remains available for remote/API work, but cannot perform local Git operations.” This is intentional protection for jj repositories, not an accidental compatibility limitation.

Failure behavior: if a gh command tries to invoke Git, it fails through the mounted Git blocker with the explicit jj/API guidance message. A separate gh shim is unnecessary because the child Git invocation receives the same diagnostic.

Agent-facing diagnostic supplied by the Git blocker

No-Git mode’s mounted git blocker supplies the diagnostic. It preserves a non-zero failure status and emits the message below:

agentbox: Git is disabled in this agentbox.
Use jj for local repository operations. Use gh with -R OWNER/REPO or gh api
for remote GitHub operations.

This gives agents an immediate explanation instead of making them spend tokens inferring why a GitHub command failed. Unrelated gh errors are unaffected because the blocker only runs when gh invokes git. A live test with gh repo clone cli/cli confirmed that gh preserves the blocker message and appends failed to run git: exit status 1.

Leading implementation candidate: mount-based Git blocker

When no-Git mode is active, mount a small read-only shell script over the image’s existing /usr/bin/git path. The real Git package remains in the image, but the mounted script masks it and exits non-zero with the jj guidance message:

agentbox: Git is disabled in this agentbox.
Use jj for local repository operations. Use gh with -R OWNER/REPO or gh api
for remote GitHub operations.

This avoids an image rebuild, avoids a second image/container, and causes both direct git calls and Git-dependent gh calls to receive the same explanation. The live gh repo clone test confirmed that the child diagnostic is preserved, so a separate gh shim is unnecessary.

The tradeoff is that a bind mount is part of container creation. Changing the policy would need the same container to be stopped and recreated with the alternate mount, but it would not need an image build or volume destruction; the per-project Docker and jj volumes would be preserved. This is a fixed, tracked launcher asset rather than a generated temporary file: runtime/git-disabled relative to the Agentbox launcher root. The implementation includes this file with executable mode 0755. At runtime it is mounted read-only from the host over /usr/bin/git, and the mount disappears automatically when that container is removed. Blocker validation is intentionally attribute-only: the launcher requires a regular, non-symlink, readable, executable, non-world-writable file with mode 0755, but does not hash or execute the source during preflight. The tracked asset’s content and diagnostic are repository/runtime acceptance concerns, not a hostile-host integrity guarantee. The source need not be root-owned—the launcher user and Docker daemon only need read access, and the container cannot modify it through the read-only mount. The source is resolved relative to the launcher, not AGENTBOX_CONTEXT, so a custom build context cannot make the blocker unavailable.

When Git is enabled, no blocker mount is present. When Git is disabled, the blocker is the only new immutable mount required; the real Git package remains in the image and the ordinary-agent threat-model limitation above still applies.

Proposed persistent policy config

Use a dedicated agentbox.toml at each existing configuration tier:

~/.config/agentbox/agentbox.toml
~/.config/agentbox/machines/<machine>/agentbox.toml
~/.config/agentbox/projects/<project-path>/agentbox.toml
~/.config/agentbox/machines/<machine>/projects/<project-path>/agentbox.toml

The file would contain launcher policies rather than ordinary container environment values:

[git]
enabled = false

[github]
grant = true

[ssh]
grant_all = true

[updates]
check = false

The existing env files remain purely for environment variables inside the containers. They should not carry Agentbox launcher policy. The launcher reads agentbox.toml before container creation, using the same global/machine/project hierarchy. Agentbox policy files inherit field-by-field from global to machine to project to machine/project; a more-specific file overrides only keys it defines, including setting an inherited boolean back to false.

Policy parsing is host-side, but the policy is not a secret. The existing read-only Agentbox configuration mount exposes ~/.config/agentbox inside the container, so agents may inspect the contributing files; this visibility is intentional. The files contain only launcher choices; GitHub, SSH, and other credentials remain controlled by their separate mounts and grants.

Policy-file contract

  • Only these keys are recognized initially: git.enabled, github.grant, ssh.grant_all, and updates.check.
  • agentbox.toml uses the deliberately narrow Agentbox policy grammar below; it is not a general-purpose TOML parser. Unknown keys, unknown tables, duplicate assignments, and unsupported syntax are fatal before Docker is touched.
  • The accepted grammar is: blank lines; lines whose first non-space character is #; exact table headers [git], [github], [ssh], or [updates]; and one recognized key = true or key = false assignment per fully qualified field, with whitespace around the key/value and an optional trailing # comment on an assignment. Table headers may recur, but each recognized field may be assigned only once per file. Inline header comments, quoted values, arrays, inline tables, dotted keys, and other general TOML features are invalid by design.
  • An empty or comment-only file is valid and contributes no fields. LF and CRLF line endings are accepted. Syntax errors identify the policy file, one-based line number, offending table/key or token, and a short reason; errors never fall through to a less-specific file.
  • Host policy variables accept 1/true/yes/on for true and 0/false/no/off for false, case-insensitively. An unset variable contributes no value; an invalid value is fatal.
  • The environment mappings are exact: AGENTBOX_NO_GIT=true means git.enabled = false, AGENTBOX_NO_GIT=false means git.enabled = true, and AGENTBOX_NO_UPDATE_CHECK=true means updates.check = false. Grant variables map directly to their grant fields.
  • For grant fields, an absent value preserves a persisted grant on an existing container for compatibility; an explicit false value revokes it. For a new container, absent grants resolve to false.
  • Because no positive --git flag is provided, a one-invocation Git re-enable uses AGENTBOX_NO_GIT=0; a persistent or scoped re-enable uses [git] enabled = true.
  • Policy files must be regular, readable, non-world-writable files under the user’s Agentbox configuration tree. They contain no secrets; credential files remain controlled by the existing explicit grants.
  • ab config reports every contributing agentbox.toml, the merged effective values, and the source tier for each value. It also reports the policy recorded on the existing container so stale policy is visible.
# accepted: empty contribution, whitespace, and trailing value comment
[git]
enabled = false # jj-first mode

# rejected: inline header comment, quoted boolean, and duplicate assignment
[git] # not accepted
enabled = "false"
enabled = true

Canonical digest and legacy-label migration

The policy digest is computed from one canonical UTF-8 payload after precedence, defaults, and command-specific compatibility have been resolved. The payload is exactly these newline-separated lowercase entries, in this order, with a final newline:

schema_version=1
git_enabled=true
github_grant=false
ssh_grant_all=false

Each value is normalized to the literal lowercase true or false, including explicit defaults. TOML formatting, source-tier names, omitted fields, and updates.check are not inputs. The SHA-256 of those exact bytes is recorded as sha256: followed by 64 lowercase hexadecimal characters in org.agentbox.policy.digest. Thus equivalent merged policies have the same digest, and every container-affecting effective-value change has a different digest.

Migration recognizes the existing labels agentbox.grant-gh and agentbox.grant-all-of-dot-ssh when no new org.agentbox.policy.* labels exist. A present old label must be exactly 0 or 1; a malformed value is stale/invalid and is never guessed. An absent old grant label means false, matching the old launcher’s ungranted state. For an ordinary ab start with no explicit policy, valid old labels supply the persisted grant values, while Git is treated as enabled because the old launcher had no no-Git policy. Explicit CLI, host environment, or TOML values take precedence over migrated values. A successful recreation writes the complete new versioned label set and no longer relies on the old labels.

If any new policy label is present, the complete new set must be present and valid; it is not combined with old labels. A partial, unsupported, or malformed new set is stale/invalid and requires explicit reconciliation. A no-label container that nevertheless has an unidentifiable Git-blocker mount is also treated as ambiguous/stale rather than silently enabling or disabling Git. ab config reports the legacy source, migrated values, or exact invalidity and digest delta.

Launcher entry-point policy scope

Policy is container-scoped, not a temporary per-process overlay. Every launcher entry point that can start or execute in an agentbox—ab start, ab build, ab rebuild, ab claude, ab codex, ab bash, and ab exec—uses the same policy-resolution and container-state check before it runs Docker.

  • If the container is absent or stopped, an agent/exec entry point starts or recreates it using the resolved policy before executing the requested command.
  • If the container is running with matching policy, the command proceeds.
  • If the container is running with missing, stale, or different policy, the command refuses without executing inside it. It reports the effective and recorded policy and directs the user to the explicit apply path.
  • An override such as AGENTBOX_NO_GIT=1 ab codex cannot change mounts just for that process. To apply it to a running container, use AGENTBOX_NO_GIT=1 ab start --apply, then retry ab codex or ab exec. Likewise, use AGENTBOX_NO_GIT=0 ab start --apply to re-enable Git on a running container.

Preflight and validation boundary

A host preflight phase runs after basic command/argument capture and before the update check, require_sysbox, image builds, network changes, or any Docker mutation. Help/version fast paths may return before policy work. Every other path resolves the CLI, host environment, and Agentbox policy files; validates all policy files and option combinations; and validates the no-Git blocker source when it will be needed. Therefore invalid policy syntax, unsafe policy files, invalid policy environment values, invalid blocker attributes, and invalid options produce no Docker or network side effect.

When a named container already exists, a subsequent read-only docker inspect may be used to classify its state and parse its policy labels. That inspection is not a mutation. Missing labels normally classify the container as legacy, but a no-label container with an unknown /usr/bin/git mount source is ambiguous/invalid; malformed or incomplete labels likewise classify it as stale and stop the flow before any update check, build, start, remove, or recreation. For commands that may mutate or execute in a container—and for the read-only ab config report—the update check must run only after this validation and inspection phase, and is never allowed to turn a policy error into a network operation.

Canonical configuration lookup

  • AGENTBOX_MACHINE and the hostname default use the machine-name grammar [A-Za-z0-9][A-Za-z0-9._-]{0,62}[A-Za-z0-9]; a one-character name is also valid. Invalid or path-containing names fail before lookup.
  • The project identity is the physical absolute path produced by resolving AGENTBOX_DIR with symlinks and dot components removed before configuration lookup. A symlink change that selects a different physical project therefore selects a different project tier.
  • Project path components are encoded as literal UTF-8 directory names below projects/; spaces, Unicode, nested paths, and punctuation other than / are preserved. Lookup is byte-exact and follows the host filesystem’s case sensitivity; no case folding or Unicode normalization is performed.
  • The full physical path plus the machine name identifies the policy. Two projects with the same basename do not collide, and path encoding never permits .. to escape the configuration root. A rename or case-only change is a new project identity unless the host filesystem itself treats the paths as identical.
  • Examples: /work/acme/foo bar maps below projects/work/acme/foo bar/; /home/a/app and /home/b/app remain distinct; and a symlink /work/current resolves to the physical target before selecting a tier.

Apply atomicity and failure recovery

Policy application is intentionally name-preserving but not Docker-transactional. Image selection, policy parsing, blocker validation, and all read-only inspection occur before removing a running container. Once the old container is removed, a failed docker run, network attachment, or readiness step may leave the logical container absent; the named Docker/jj volumes remain preserved and reusable. The launcher must report the failed phase, container name, image tag, and volume names, and ab config must report “absent after failed recreation” rather than implying that the old container still exists.

Every replacement attempt also writes a durable host-side operation record at $XDG_STATE_HOME/agentbox/operations/<sha256(physical-project-path + NUL + machine)>.toml, defaulting to ~/.local/state when XDG_STATE_HOME is unset. The directory is mode 0700, records are mode 0600, and updates use a temporary file plus atomic rename. A record contains an operation id, start/end time, phase, status, container name and ids when known, policy digest, image reference, named-volume names, network outcomes, and a diagnostic; it never contains policy-file contents, credential paths, tokens, or mounted credential data. The physical path is represented by the filename hash rather than stored in the record.

The record is written before removal and updated after each phase: preflight, removal, creation, required-network attachment, nested readiness, and completion. A successful replacement is complete only after the container is inspectable with the expected mounts/labels and required readiness checks pass; then the completed record may be removed. A failed docker rm -f is recorded as removal-failed; the launcher must not attempt a same-name create until a fresh inspect establishes the old container’s exact state. If removal succeeded but creation or required network attachment fails, the record is absent-after-failure and ordinary start/exec refuse until an explicit retry. A configured optional network remains best-effort, but its failure is recorded as network-degraded and shown by ab config. A readiness failure is recorded separately as readiness-failed, including whether the outer container is running and whether the nested daemon is ready.

ab config reports any non-complete operation record and the exact retry command, and a failed record prevents ordinary execution from using an old or partially recreated container. ab start --apply or ab rebuild retries from a new inspection; it never assumes rollback or that the old container remains usable. Named Docker/jj volumes are preserved in every case. No automatic rollback claims are made because Docker cannot atomically replace a container with the same name.

Credential-grant source validation

A requested credential grant is all-or-nothing and is validated before any Docker or network mutation. A GitHub grant requires ~/.config/gh to exist as a readable, searchable, non-symlink directory. An empty directory is valid and is mounted, but does not imply that credentials exist. A missing, unreadable, symlinked, non-directory, or otherwise unexpected source fails the requested grant with a stable diagnostic; the launcher does not silently record the grant as enabled without the mount.

A full-SSH grant requires ~/.ssh to be a readable, searchable, non-symlink directory. The directory is mounted read-only; no other SSH file is writable through this grant. If known_hosts exists, it must be a regular readable, host-user-writable, non-symlink file and is mounted read-write at the protected destination so host-key additions persist. If it is absent, the grant still succeeds without a known_hosts mount, and SSH host-key persistence is unavailable until the host file is created. A symlink, directory, device, unreadable file, non-writable file, or other unexpected known_hosts type fails the requested grant before mutation. A successful policy label is written only after the corresponding mount is present and inspectable.

Policy snapshot and source-change consistency

After acquiring the per-project lock, the launcher reads every applicable policy file and host-policy value into one immutable in-memory snapshot. Resolution, digest calculation, preflight diagnostics, mount decisions, and label rendering all use that snapshot; no later phase rereads a policy file opportunistically. The snapshot records each source path, filesystem identity and metadata, and SHA-256 content hash for reporting without exposing file contents. The hash already encodes content length, so no separate byte-length field is maintained.

Immediately before the first Docker mutation, the launcher re-stats and re-hashes every policy source. If any source changed, it discards the snapshot, rereads the complete policy set, and retries preflight once. If a source changes again, the operation fails as policy-changed-during-resolution with no Docker mutation, and ab config reports the source path and retry command. The same snapshot and hashes label the operation record, so a config report can distinguish a policy change from a container-state change.

Protected mount destinations and conflicts

The launcher reserves these destinations for policy-controlled mounts: /usr/bin/git, /home/agentbox/.gitconfig, /home/agentbox/.config/git/config, /home/agentbox/.config/gh, /home/agentbox/.ssh, and /home/agentbox/.ssh/known_hosts. A custom mounts entry targeting one of these paths, or a parent mount that would obscure one of them, is rejected during host preflight. Custom mounts never override, shadow, or replace a policy mount.

ab config reports the conflicting source and protected destination. Because the custom entry is rejected before Docker work, the ordinary no-Git guarantee is not weakened by user configuration; the broader threat-model disclaimer still applies to alternate Git binaries and mounts outside these protected paths.

Policy-label versioning and migration

  • Version 1 requires the complete known label set and the SHA-256 digest algorithm defined above. Extra labels in the org.agentbox.policy.* namespace are unsupported metadata and make the recorded state stale until reconciled.
  • A higher, unknown policy version is never interpreted, downgraded, or combined with old labels. Normal start/exec/config paths report unsupported-version state; explicit start --apply with the current launcher replaces it using the current resolved policy.
  • Legacy labels are read only when no new policy labels exist. Successful reconciliation writes the complete current set; old compatibility labels may remain for inspection but are no longer authoritative. Migration is one-way for a container: an older launcher encountering a higher version must refuse rather than silently rewrite it.
  • Partial labels, missing fields, digest-algorithm changes, or partial migration are ambiguous. Explicit reconciliation uses current host policy values; absent or ambiguous credential values default to revoked rather than being preserved by inference.

Deterministic acceptance and network scope

Local acceptance cases are deterministic and require exact exit status, diagnostic substring, mount expectation, label expectation, and cleanup. The no-Git direct check requires exit status non-zero and the exact first line agentbox: Git is disabled in this agentbox.; the jj check requires exit status zero and the expected workspace root; the Git config check requires absence of both protected Git config destinations in no-Git mode. GitHub CLI checks require gh --version to succeed locally and a Git-dependent operation to fail through the blocker when run against the fixture repository.

Remote/API GitHub operations are best-effort integration checks, separate from the local acceptance gate. They run only when explicit test credentials and network access are supplied; repository, authentication, rate-limit, and offline failures are reported as environmental skips, not product passes or failures. The core no-Git acceptance suite never contacts GitHub.

Update-check scope and concurrency

updates.check participates in the same four-tier field inheritance as the other policy fields: machine/project policy may override global policy, and host AGENTBOX_NO_UPDATE_CHECK overrides merged TOML. It is host-only, affects future invocations, never enters the container digest, and never causes recreation. The update request is allowed only after the relevant read-only policy/container inspection succeeds.

All policy-sensitive launcher operations for one project—start, start --apply, build, rebuild, auto-starting execution paths, and config—take one per-project advisory lock before inspection and hold it through policy snapshotting, any stop/remove/create/start/network operation, and the final report. The lock identity is the SHA-256 of the physical project path plus a NUL byte plus the machine name. The lock file is $XDG_RUNTIME_DIR/agentbox/locks/<hash>.lock, falling back to $XDG_CACHE_HOME/agentbox/locks/<hash>.lock and then ~/.cache/agentbox/locks/<hash>.lock; the directory is mode 0700 and the lock file is mode 0600.

The launcher waits at most 30 seconds, polling at a bounded interval. A busy lock returns a distinct non-zero “project busy” diagnostic containing the project/container identity and a retry hint; an inability to create, open, or lock the path returns a distinct “lock failed” diagnostic and never proceeds unlocked. Read-only config, status inspection, and policy-file initialization participate in the same lock so their reports cannot straddle a replacement; help/version paths do not take it. The launcher does not recursively acquire the same lock: child operations inherit the already-held lock context, and a second independent process must wait or fail by the same timeout rule. After acquiring the lock, it re-inspects policy and container identity before mutation and reports the final recorded state after mutation.

Nested-Docker restart recovery contract

Outer-container stop/start must preserve the named /var/lib/docker volume and recover the nested daemon without launching duplicate dockerd processes. After an initial docker info failure, recovery must inspect both the Docker PID file and the process table. A process-table match is valid only when the process identity is explicitly dockerd; a missing, unreadable, stale, or mismatched PID file must not by itself authorize socket/PID cleanup. If a live dockerd is found, the entrypoint waits for its socket/API to become ready. Only after no matching daemon is alive may it remove stale /var/run/docker.sock and /var/run/docker.pid markers and start one replacement daemon.

The readiness state machine is: starting (a launch has been requested), ready (the Docker API answers), failed-but-running (a matching non-zombie dockerd remains but the bounded readiness wait expired), failed-and-exited (the attempted daemon is gone before readiness), and replacement-attempted (the one permitted retry has been launched and classified). The outer container remains running in every failure state so that status, logs, config, and stop remain available. status reports the outer state, nested readiness state, operation id, and retryability; logs exposes the entrypoint/nested-daemon diagnostic and failed phase; config reports the operation record, policy snapshot hash, and exact retry command. Generic ab exec is not blocked by nested readiness, but commands that require the inner Docker API return a distinct “nested Docker not ready” diagnostic.

The bounded readiness wait is 30 seconds. The recovery path first handles starting to ready, or to failed-but-running/failed-and-exited. Only failed-and-exited permits stale-marker cleanup and one synchronous replacement attempt; a live-but-never-ready daemon never permits a duplicate. After replacement-attempted reaches a terminal failure, a later outer ab start reports the stored state rather than spawning another daemon; an explicit outer stop/start is required for a fresh recovery cycle. The focused acceptance cases are live daemon with a valid PID file, live daemon with no usable PID file, stale socket/PID markers with no daemon, daemon exit during readiness, and persistent non-ready daemon. Each case must prove at most one nested dockerd is started, that the API becomes usable when recovery succeeds, and that the named Docker volume and existing inner-Docker state remain intact.

Working recommendation

Treat --no-git/AGENTBOX_NO_GIT, --grant-gh/AGENTBOX_GRANT_GH, --grant-all-of-dot-ssh/AGENTBOX_GRANT_ALL_OF_DOT_SSH, and AGENTBOX_NO_UPDATE_CHECK as host launcher policies. Git config mounts should be omitted when disabled; GitHub and SSH credentials remain independently controllable.

Apply and observability contract

  • All launcher entry points resolve and host-validate the effective policy before they check, start, build, recreate, or execute in a container. ab start and every convenience/exec command must not silently use a container whose policy labels differ from the resolved policy.
  • If the named container is stopped or absent, ab start may stop/remove and recreate it using the existing image/tag and existing named volumes. If it is running and policy differs, ordinary ab start refuses with the mismatch and the warning that active agents, inner Docker state, and other container-local state would be interrupted.
  • ab start --apply is the explicit policy-application path for a running container. It warns, then stops/removes and recreates the same named container. It preserves the project bind mount, inner-Docker volume, and jj volume; container-local filesystem changes are not promised to survive.
  • New containers record a complete versioned set of effective container-policy labels, for example org.agentbox.policy.version=1, org.agentbox.policy.git_enabled=true, org.agentbox.policy.github_grant=false, org.agentbox.policy.ssh_grant_all=false, and org.agentbox.policy.digest=sha256:.... The digest covers container-affecting policy only; the host-only update-check setting is excluded.
  • A container with none of the policy labels is legacy when its Git mount state is known: no blocker mount means Git enabled, and Agentbox’s recognized blocker means Git disabled. An unknown or uninspectable /usr/bin/git mount, or a contradictory legacy credential mount, is stale/invalid. A container with a partial label set, unsupported version, invalid boolean, malformed digest, or other inconsistent policy metadata is likewise stale/invalid, not legacy; normal commands refuse before mutation and require explicit ab start --apply. A valid label set with a digest mismatch is stale and reports both the effective and recorded values before refusing when running.
  • Versioned labels are not authoritative by themselves: read-only inspection must compare the recorded booleans with the actual mounts. git_enabled=false requires Agentbox’s recognized blocker at /usr/bin/git and no Git config mount; git_enabled=true requires no blocker mount. github_grant and ssh_grant_all each require presence or absence of their corresponding credential mount. Any contradiction is stale/invalid, and ab config reports the exact label-versus-mount delta.
  • For a legacy or existing valid labeled container, omitted grant policy adopts the persisted grant labels for ab start; the command-specific ab build/ab rebuild rule above applies for rebuilds. An explicit false policy removes the corresponding grant mount and records the revoked state.
  • ab config shows the merged policy, contributing files, value sources, the parsed recorded labels, and the running/container policy comparison including exact effective-versus-recorded deltas. This makes stale security state visible before an agent is launched.
